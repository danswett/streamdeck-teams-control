**Environment:** Teams 26262.500.5142.2903, WebView2 153.0.4234.48, live meeting with a deck shared

## Method

Three independent passes:

1. **A hostile CDP server** (`fake-cdp.mjs`) standing in for Teams, with modes
   for redirection, spoofing, oversized replies, hanging, split UTF-8 and
   target flooding. This is what turned suspicions into reproductions.
2. **An OS-sampled measurement harness** recording CPU, working set, private
   bytes, handles and threads once a second across soaks of 5, 8 and 15
   minutes, plus per-command latency timed at the sidecar's stdio boundary.
3. **A delegated security review** of the whole application, which independently
   reproduced the redirection finding and contributed the state-forgery
   consequence I had not thought through.

## Security findings

### SEC-1 — The endpoint chose where we connected (MEDIUM, fixed)

`ListTargets` took `webSocketDebuggerUrl` verbatim from the JSON and `Evaluate`
passed it to `ConnectAsync`. Whoever answered on the configured port therefore
decided the destination of the sidecar's next TCP connection — any host, any
port.

**Reproduced.** A fake endpoint on 9911 advertising a target on 9912, with the
sidecar configured only for 9911:

```
*** DECOY CONTACTED — client followed the advertised URL ***   (x4)
```

**Fixed.** `Cdp.IsConnectable` requires `ws://`, a loopback host, and the port
already configured. Re-tested: the decoy is never contacted.

### SEC-2 — Ownership was self-asserted (MEDIUM, fixed)

"Is this Teams?" was answered by reading a URL supplied by the party being
vetted (`t.Url.StartsWith("https://teams.microsoft.com/")`). Any local process
can claim that, and a browser with one Teams tab open claims it honestly while
still being the wrong thing to drive.

The consequence is worse than the access itself. The peer controls every
`Runtime.evaluate` reply; `Interpret` trusts `{"ok":true}`, and `checkedBefore`
from that reply is written into `_lastStates`, which drives what the key
renders. **A port-holder could make the deck show muted while the microphone
was live.** For a meeting tool that matters more than the connection.

**Fixed.** Ownership now comes from the operating system —
`GetExtendedTcpTable` for the PID holding the socket, `Toolhelp32` to walk its
ancestry — not from anything the peer says.

> **I got this wrong first, and only caught it by testing against real Teams.**
> Checking the direct owner rejected the genuine port: a WebView2 application
> does not open the port itself, so the socket belongs to `msedgewebview2.exe`,
> whose parent is `ms-teams.exe`. My "strong fix" disabled the feature. The
> ancestry walk is the correct check.

### SEC-3 — Unbounded replies (MEDIUM, fixed)

The receive loop appended without a ceiling.

**Measured.** A 40 MB reply drove the sidecar from 58 MB to **402 MB** of
working set — roughly 7× the payload, because bytes are decoded to UTF-16 and
then parsed. A larger one exhausts memory.

**Fixed.** 8 MB cap on a reply, 1 MB on a discovery document.

### SEC-4 — Discovery could stall every key press (MEDIUM, fixed)

Probing tried each Teams-looking page in turn, each with its own timeout, on
the single worker thread that also serves key presses.

**Measured.** Sixty targets, each stalling: **90,761 ms** before the sidecar
answered. For a minute and a half no key would have worked.

**Fixed.** Discovery stops after eight candidates. Teams keeps a handful.

## Correctness findings

| # | Issue | Status |
|---|---|---|
| C-1 | Replies were decoded **per chunk**, so a receive boundary landing inside a multi-byte character corrupts it. Did not reproduce on the run attempted — chunk alignment is a race — but it is unsound by construction. | Fixed: bytes accumulated, decoded once |
| C-2 | `{arg}` was regex-escaped on the accessibility path but not on the direct one, so one config entry meant a literal on one and live regex syntax on the other — and reached `new RegExp` in the page, where there is no match timeout. | Fixed: `forRegex` on both |
| C-3 | Two timer regexes compiled without `ControlSpec.MatchTimeout`. Currently unreachable *only because the config parsing is unimplemented* — which the README already documents as supported. Implementing it would have created a ReDoS on the worker thread in the same commit. | Fixed pre-emptively |
| C-4 | The slide-show target was matched by `Contains("slideshow.aspx")`, which a query string satisfies. | Fixed: host and path checked |

Also removed: a dead ternary whose branches were identical.

## Performance

### Measured cost

15-minute soak, 147 presses, sampled once a second from the OS:

| | CPU avg | CPU p95 | CPU max | working set | private (steady) |
|---|---|---|---|---|---|
| Accessibility path | 0.28% | 0.77% | 1.36% | 14–89 MB | ~40 MB |
| Direct mode | 0.27% | 0.77% | 1.87% | 33–96 MB | ~46 MB |

**Direct mode costs no more CPU than the accessibility path.**

Per-operation, timed at the sidecar's own boundary:

| Operation | Time |
|---|---|
| Reaction, accessibility path | 1.4–1.9 s (flyout visible) |
| Reaction, Direct mode | ~0.3 s (nothing visible) |
| Thumbnail 200×100 | 254–381 ms |
| Thumbnail 1024×1024 | ~414 ms |
| Full state snapshot | 571–950 ms |
| First state after launch | 1.4–3.7 s |
| `directmode` probe | 89 ms |

### PERF-1 — A real handle leak (fixed)

`GetSnapshot` called `Process.GetProcessesByName("ms-teams").Length` on **every
poll** — every three seconds in a meeting — and never disposed the objects, each
of which holds an OS handle until finalization.

**Measured effect of the fix:** steady-state handles **564 → 541**, private bytes
**45.4 → 40.0 MB**.

### PERF-2 — What is *not* a leak

Worth stating because it was my first suspicion. Over 15 minutes and 147
presses, handles **plateau** at ~565 from minute 10, and private bytes at ~46 MB
from minute 6. Working set sawtooths — the sidecar returns memory on a timer,
every 5 minutes during a meeting — so a short sample reads as growth when it is
a cycle. Neither is unbounded.

### PERF-3 — Documentation was wrong in both directions

The README claimed 1.0% CPU and 22.5 MB working set. Measured: **0.27% average**
(better than claimed) and **33–96 MB** (substantially worse). Both corrected,
with the sawtooth explained rather than a single number quoted.

### Not fixed, worth knowing

The sidecar logs `slow snapshot: 3609ms (a press during this would have
waited)` on its first snapshot after launch. That is the index build, it is
already self-reported, and the single-worker design means it delays a press
that arrives during it. Left alone: it happens once per launch, and the fix is
a concurrency change that deserves its own consideration.

## Architecture — verified, not assumed

- **Threading.** One MTA worker thread; all work arrives through a
  `BlockingCollection`. UIA event callbacks only enqueue. So `TeamsClient` and
  `DomActuator` state needs no synchronisation — checked rather than hoped.
- **Lifecycle.** `TeamsClient.Dispose` clears watches, unregisters events,
  disposes the automation object. Correct.
- **Fallback.** Direct mode returns a tri-state — declined / ok / failed — so a
  control it cannot drive falls through silently, and a genuine failure is
  logged before the same fallback. Verified live: a wrong port yields
  `"no debugging port on 9999"` and the press still succeeds through UI
  Automation.
- **Window-handle reuse.** The set of nudged windows was never cleared, and
  Windows recycles handles — a new window inheriting a closed one's handle would
  never be woken, which looks exactly like not being in a meeting. Now bounded.

## Cleared — checked and fine

From the delegated review, verified against the real code rather than assumed:

- **JavaScript escaping is airtight.** 17 breakout vectors — quote-and-reopen,
  backslash-eat, `</script>`, template-literal syntax, U+2028/U+2029, NUL —
  through the real `Js`/`JsArray`/`Fill` and the real templates. Every hostile
  value stayed inside its literal.
- **`m_slideIndex` can only be an integer** (`int.TryParse`, negative rejected,
  `InvariantGlobalization` on).
- **`postMessage(…, '*')` is acceptable** — the payload is a slide index and an
  id read from the local DOM. No token, no content.
- **`InputPoster` cannot target the wrong window** — handle re-derived per
  window change, re-validated at post time, no wire-supplied coordinates.
- **`SlideCapture` cannot capture what it should not** — rectangles outside the
  window are rejected; geometry comes from UIA, never the wire.
- **No prototype pollution** in `protocol.ts`.
- **Privacy holds.** Nothing new logs, transmits or persists meeting content,
  participant names, window titles or tokens.
- **Consume-only holds.** No `SetEnvironmentVariable`, no `Registry`, no
  `Process.Start` in shipped code. The only occurrences repo-wide are PowerShell
  snippets in `docs/direct-mode.md` for the user to run by hand.

## Outstanding

1. **`adm-zip@0.6.1`** resolves in `package-lock.json` from a
   `pkgs.visualstudio.com` feed rather than npmjs — **resolved**: the version is
   genuine and public (published 2026-09-11), the integrity hash pins the
   content, and it is 1 of 213 entries. It is a proxy-URL artifact of the
   machine that ran `npm install`, not a supply-chain problem. CI restores it
   successfully. Worth normalising the URL at some point so an external
   contributor can `npm ci`.
2. **The first snapshot blocks presses** (above). Design question, not a defect.
3. **The ownership check trusts process ancestry.** That is a large improvement
   on trusting a URL, but a process running as the user can still, in principle,
   arrange to be `ms-teams.exe`'s child. At that point it can also read the
   token cache directly, so this is the right place to stop.
4. **Dismissing the "Change view" menu costs ~4 s on the accessibility path.**
   Measured to the rung: `natural=1531ms refind=31ms collapseCall=2032ms`. The
   time is inside Teams' own `ExpandCollapsePattern.Collapse()`, which blocks
   for two seconds on this control before returning — not in the search, the
   wait, or the detection. Nothing on this side can reorder that away, and a
   speculative change to the surrounding timings was deliberately not made.
   Direct mode does not have the problem, because it never opens the menu
   visibly and closes it with a key event.

## Post-merge review round (PR #3)

Two P2 findings came back from automated review after merge. Both were real and
both are fixed.

### R-1 — The hit test asked the screen, not the window (fixed)

`OccupiedAt` used `FromPoint`, which resolves the topmost element at a screen
coordinate across **all** applications. The plugin's entire design is that Teams
sits behind whatever the user is working in, so this inspected the wrong
application almost every time.

**Measured with Teams unfocused:** three of the five dismissal candidates
resolved to the terminal window on top of Teams, and the other two to the
WebView2 render process — none to the meeting window. Every point therefore
looked unoccupied, and the exclusions that stop a dismissal click landing on a
participant tile were bypassed.

This was my own optimisation from the previous round, and the A/B measurement
had already shown it bought nothing. **Reverted** to enumerating the window's own
tree, with the reasoning recorded in the code so it is not reintroduced.

### R-2 — A config regex could freeze Teams (fixed)

`menuItemName` and `menuItemOffName` were compiled by the page's own regex
engine. JavaScript has no match timeout, and the CDP timeout abandons the socket
without interrupting a regex already running — so a backtracking pattern would
have frozen the user's Teams window rather than failing a key press.

**Fixed** by declining name-matched controls on the direct path entirely: they
fall back to UI Automation, which matches under `ControlSpec.MatchTimeout`. The
regex machinery is gone from the generated script, and a test asserts no
`RegExp` can appear in it. Only the background-effect entries match by name, so
the cost is one flyout staying visible.

### R-3 — Grid view could be left stuck open (found by functional testing)

Not from the review — found by exercising every action end to end.

`ppt-grid` opens from the slide toolbar and closes from a button *inside the
overlay it opens*, matched by name. `InvokeCore` has dedicated logic for that;
`DomActuator` never did, so it clicked the opener again and the grid stayed up.

That is not a one-press failure. An open grid unmounts the whole slide-show
subtree, so it took slide position, all five ink tools, presenter view, high
contrast, copy link and thumbnails down with it — **six further failures from
one root cause**, which is exactly what the functional test showed before the
fix and does not show after.

**Fixed** by declining any control with an off-selector, and any control behind a
nested menu, to the accessibility path.

## Functional test

A new harness drives every safe action through the real sidecar, checks the
observable consequence rather than the return code, and restores what it
changed. Run against a live meeting with a deck shared, on both paths:

| Path | Result |
|---|---|
| UI Automation | **33 passed, 0 failed** |
| Direct mode | **33 passed, 0 failed** |

Covered: five reactions and raise hand; background blur on and off; chat and
people panes; a hard-muted microphone correctly refusing rather than claiming
success; slide next/prev across animation builds; an arbitrary slide jump; grid
view; private viewing; presenter view; high contrast; copy link; content-only
layout; all five ink tools with restoration; current and next thumbnails; a
timer that is not running; and a check that the deck is left where it started
and still being presented.

Two apparent failures in the first run were the harness being wrong, not the
product: `chat`/`people` report availability only and have no state to flip, and
`ppt-next` steps animation builds before it changes slide — verified by pressing
it six times and watching it advance 2→2→3→4→5→6→7, which is what the on-screen
button does.
