## Findings

### F-1 — Closing a flyout could leave Teams in front (MEDIUM, fixed in #19)

Reported by Kyle von Haden while testing #17, and reproducible with Background
Blur on the release plugin. A press runs under the focus guard, but the
flyout it opened is closed after the press returns, by which time the guard
has stopped watching. When click-away cannot be used, because a deck is being
presented or every candidate point is covered, `DismissFlyout` falls back to
UI Automation `Collapse`, and then to `Invoke` on the popup's ancestors. Both
activate the Teams window.

| build | Teams in front after a flyout press | Teams keeps focus |
|---|---|---|
| `main` before #19 | 1.8–2.2 s | yes, never restored |
| #19 | 65–190 ms | no |

Every slow-flyout log in the A/B named the `dismiss:collapse` step.
`test-focus-strict.ps1` had stopped sampling at 2.5 s, before that step runs,
which is how this went unnoticed. It now samples until the cleanup has
finished. The remaining flash is #20.

### F-2 — A webcam press with nothing to do took the same fallback (LOW, fixed)

Found by reading the cleanup path while preparing the camera test. The cleanup
clicked away only "after a press actually landed". Change Camera pressed for
the webcam already in use correctly presses nothing, so its menu was left to
`DismissFlyout`. It never closes on its own, so after 1.5 s it reached
`Collapse` and brought Teams forward on every such press. Before #19, nothing
would have put focus back. Error paths that leave the menu open behave the same
way: an entry Teams has greyed out, or a swap pair Teams cannot offer.

The original concern was clicking into the meeting when the menu might never
have opened. Finding the item proves that the menu opened, so the cleanup now
clicks away whenever the item was found.

**Measured after the fix:** the repeat press logged `settle=217ms away=60ms
dismiss=68ms`, and the foreground never changed.

### F-3 — Swap Camera looked up its second webcam without the selector template (LOW, fixed)

The first webcam's lookup went through `Fill` with the control's id, toggle id
and name templates. The second was searched by its raw device id. Today the
template is exactly `{arg}`, so the two matched. But `selectors.json` is where
selectors are corrected after a Teams update, and a wrapped template such as
`camera-{arg}` would have reached the first webcam only, leaving every swap
failing on the second.

Both lookups now go through `TryItemSelectors`. A test runs a swap pair through
a template with a prefix and a name pattern.

### F-4 — Camera, Change Camera and Swap Camera shared one icon file (LOW, fixed)

They were the only actions out of 40 sharing artwork files, both in the action
list and on the key. 1.9.9 had already removed duplicate marks from the list
for the ink dials. Change Camera now draws Fluent's `video_usb` and Swap Camera
`video_multiple`, both from the same 28px tier as every other meeting control.
The keys draw the same glyphs at runtime. `tests/marketplace.test.ts` now fails
if two actions point at one icon file.

### F-5 — The macOS sidecar reads every element's frame on every walk (LOW, not fixed)

`Tree.walk` reads every element's frame, which only `discover` uses, so every
poll and flyout press pays for it. This affects the macOS test build only, and
nothing in CI runs that sidecar against Teams. Tracked in #21.

## Live functional test

`sidecar/test-cameras.ps1`, new in this review, ran against the trimmed
Release build. Teams listed RGB-IR Camera, Cam Link 4K and NVIDIA Broadcast,
and started on Cam Link 4K with the camera on. Teams' own selection was read
back through UI Automation after every press.

| step | result | selected afterwards | camera on | focus |
|---|---|---|---|---|
| Change to RGB-IR | ok | RGB-IR | yes | unchanged |
| Press it again | ok, nothing to do | RGB-IR | yes | unchanged |
| Swap from the second | ok | Cam Link 4K | yes | unchanged |
| Swap from the first | ok | RGB-IR | yes | unchanged |
| Change back | ok | Cam Link 4K | yes | unchanged |
| Swap a webcam with itself | refused: "choose two different webcams" | Cam Link 4K | yes | unchanged |
| Change to a missing webcam | refused: "not found in menu" | Cam Link 4K | yes | unchanged |

That settles what the code review could not: Teams' menu items carry exactly
the device ids Windows enumerates, and the menu stays open long enough for
each selection to be confirmed.

## Release readiness

- **The package.** Against v1.10.2, the only new file is the camera settings
  page, `ui/camera-select.html`, plus the two new icon folders in this branch.
  Nothing was removed, and no macOS binary, log or test file is packed.
  `streamdeck validate` and `pack` both pass.
- **The 1.9.x line.** Nothing fixed there is missing from `main`. Only two
  commits lack an equivalent patch: the 1.9.11 version bump, and 1.9.10's
  backport of the DRM-safe profile list, which `main` has carried since
  1.10.1.
- **What Marketplace users run.** The copy installed on the review machine has
  an encrypted manifest with an `ELGATO` header, so it came through Maker
  Console. Its `plugin.js` is byte-identical to the v1.9.11 release asset.
- **DRM.** That same encrypted build switches profiles: its log shows
  `-> "profiles/Teams Meeting (+ XL)"` and `-> restored`. The 1.10.1 notes
  left this as "still unverified", and it is now verified in practice. 1.11.0
  reads nothing protected at runtime either.

## Cleared — checked and fine

- `Cameras.Enumerate`: the GUIDs and COM signatures are right, and every COM
  object is released on every path, including a device that fails part-way.
- `FocusGuard.Watch`: the deadline can only be set once, the watcher cannot
  keep the process alive, and `Guarded` disposes even when the call throws.
  `RestoreAfter` behaves exactly as before.
- Property inspector: webcam names reach the page only as escaped option
  labels and `textContent`. A saved id that has disappeared falls back to the
  placeholder, so choosing again saves.
- Bad settings: a missing, empty or duplicated swap pair, or no webcam chosen,
  each returns a reason the key shows as an alert.
- `sidecar-exec.ts` does nothing on Windows, never throws, and only touches the
  resolved sidecar path.
- `bridge.ts` validates the webcam list it is sent, and a failed spawn
  schedules a restart.
- Manifest: both UUIDs are unique and registered, their images and inspector
  exist, and both are Keypad-only.
- Workflows: fork PRs get no secrets, a dispatch input reaches `run:` only
  through `env`, and the macOS test build runs only from `main` or by hand.
- Generated files: a full build leaves the tree unchanged, so the committed
  profiles and glyphs match their sources.
- The glyph and icon generators are deterministic. Regenerating added the two
  new glyphs and folders and changed nothing else.
- The camera actions keep video on or off exactly as it was, measured above.
- No camera step changed the foreground window, measured above.
